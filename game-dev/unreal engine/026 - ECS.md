# Entity Component System (ECS)

- A data-oriented architectural pattern where:
  - entities are indices
  - components are data found at those indices
  - systems & functions operated on entities matching a particular set of components
- **Data Oriented Design (DOD)**: Code designed on how memory is accessed by the CPU.
- Unreal's ECS: **Mass Framework**

## Tips & Tricks

- In ECS using **tick** is usually better than **events**.
  - i.e.: should iterate over all relevant components during tick and update state as needed.

```c++
void HealthZeroProcessor::SetRequirements() {
  ExcludeTag(Dead);
  Reads(HealthFragment);
}

void HealthZeroProcessor::ForEachEntity(HealthFragment& Health) {
  if (Health.Current <= 0) {
    AddTag(Dead);
  }
}
```

- **Entities** are not **Actors**.
  - An entity is just a piece of memory that includes specific data.
  - Entities do not need to have a world representation (visual or otherwise).
  - An entity rarely needs allocation to spawn.

```c++
void CreateDamageEvent(EntityHandle Target, float Damage) {
  CreateEntity(DamageEvent{Target, Damage});
}

void AOEDamageProcessor::SetRequirements() {
  Calls(CreateDamageEvent);
  Reads(AOEDamageFragment);
  Reads(Location);
}

void AOEDamageProcessor::ForEachEntity(...) {
  ForEachEntityInRadius(Location, AOEDamageFragment.Radius) {
    CreateDamageFragment(Entity, AOEDamageFragment.Damage);
  }
}

void DamageEventProcessor::SetRequirements() {
  Reads(DamageEvent);
  WritesIndirect(HealthFragment);
}

void DamageEventProcessor::ForEachEntity(...) {
  Health = GetFragment<HealthFragment>(Event.Target);
  Health.Current -= Event.Damage;
  DestroyEntity(Self);
}
```

- Entities should be _atomic_.
  - Each type of entity should be responsible for one or two things only.
    - Example categories:
      - Identity
      - Transform & Movement
      - Hierarchy / Pieces
      - State System
      - Pre-State Behaviour
      - Combat / Health
      - Reservation / Projectiles
- Avoid monolithic fragments.
  - Multiple fragments allow for efficient memory usage and parallelism.
- The same for Processors; each processor should be working on one/two fragments only.
- Use proper data types:
  - **tag**: a fragment with no data on it.
    - Favour tags over flags to limit branching on code flows; branching on tags happens during preparation while on flags happens processing.
  - **chunk**: the memory allocation unit for entities; a predefined size of memory.
  - **shared**: used for hierarchical processing by both presence and values
  - **sparse**: separate data-store that does not affect the entity's composition

| ...            | Data Storage                    | Affects entity archetype? |
| -------------- | ------------------------------- | ------------------------- |
| Fragment       | 1 instance/entity in chunks     | By presence               |
| Tag            | None                            | By presence               |
| ChunkFragment  | 1 instance/chunk                | By presence               |
| SharedFragment | 1 instance per shared value set | Presence and value        |
| SparseFragment | 1/entity                        | No                        |

- Hybrid ECS/Actor systems are costly, prone to buggy behaviours, and require doubling a lot of code and/or flows, so they should be avoided.
  - Complex coordinated behaviours are better for ECS; shared state and coordination logic maps should be used.

## Mass

- Plugins:
  - Mass Entity
  - Mass AI
  - Mass Crowd
  - Mass Gameplay
- Project Dependencies (`ProjectName.Build.cs`): `PrivateDependencyModuleNames.AddRange("MassEntity", "MassCommon", "MassActors", "MassLOD", "MassRepresentation")`
- General flow:
  - Create `Mass Entity Config Asset`
    - Define the list of traits for the entity.
  - Add a `Mass Spawner` in the scene, which will control the entity creation in the scene.
  - Add functionality (fragments & processors) through C++.
    - Create a `Mass Entity Trait Base`.
    - Create classes inheriting from `FMassFragment` to store pieces of data for the entities.
    - Attach fragments to entities through templating.
    - Then manipulate the data to add functionality through processors.

```c++
USTRUCT()
struct FSimpleMovementFragment : public FMassFragment {
  GENERATED_BODY()
  FVector Target;
}

UCLASS()
class USimpleRandomMovementTrait : public UMassEntityTraitBase {
  GENERATED_BODY()

protected:
  virtual void BuildTemplate(FMassEntityTemplateBuildContext& BuildContext, UWorld& World) const override;
}

void USimpleRandomMovementTrait::BuildTemplate(FMassEntityTemplateBuildContext& BuildContext, UWorld& World) const {
  BuildContext.AddFragment<FSimpleMovementFragment>();
}

UCLASS()
class USimpleRandomMovementProcessor : public UMassProcessor {
  GENERATED_BODY()

public:
  USimpleRandomMovementProcessor();

protected:
  virtual void ConfigureQueries() override;
  virtual void Execute(UMassEntitySubsystem& EntitySubsystem, FMassExecutionContext& Context) override;

private:
  FMassEntityQuery EntityQuery;

}

USimpleRandomMovementProcessor::USimpleRandomMovementProcessor() {
  bAutoRegisterWithProcessingPhases = true;
  ExecutionFlags = (int32)EProcessorExecutionFlags::All;
  ExecutionOrder.ExecuteBefore.Add(UE::Mass::ProcessorGroupNames::Avoidance);
}

void USimpleRandomMovementProcessor::ConfigureQueries() {
  EntityQuery.AddRequirement<FTransformFragment>(EMassFragmentAccess::ReadWrite);
  EntityQuery.AddRequirement<FSimpleMovementFragment>(EMassFragmentAccess::ReadWrite);
}

void USimpleRandomMovementProcessor::Execute(UMassEntitySubsystem& EntitySubsystem, FMassExecutionContext& Context) {

  EntityQuery.ForEachEntityChunk(EntitySubsystem, Context, ([this](FMassExecutionContext& Context))) {
    const TArrayView<FTransformTarget> TransformList = Context.GetMutableFragmentView<FTransformFragment>();
    const TArrayView<FSimpleMovementFragment> SimpleMovementList = Context.GetMutableFragmentView<FSimpleMovementFragment>();
    const float WorldDeltaTime = Context.GetDeltaTimeSeconds();

    for (int32 EntityIndex = 0; EntityIndex < Context.GetNumEntities(); ++EntityIndex) {
      FTransform& Transform = TransformList[EntityIndex].GetMutableTransform();
      FVector& MoveTarget = SimpleMovementList[EntityIndex].Target();

      FVector CurrentLocation = Transform.GetLocation();
      FVector TargetVector = MoveTarget - CurrentLocation;

      if (TargetVector.Size() <= 20.0f) {
        MoveTarget = FVector(FMath::RandRange(-1.f, 1.f) * 1000.f, FMath::RandRange(-1.f, 1.f) * 1000.f, CurrentLocation.Z);
      }
      else {
        Transform.SetLocation(CurrentLocation + TargetLocation.GetSafeNormal() * 400.f * WorldDeltaTime);
      }
    }
  };
}
```

### Mass Settings

- Settings for the mass system can be defined in a c++ file.

```c++
UCLASS(Config = Game, DefaultConfig, meta = (DisplayName = "Hostile Mass Settings"))
class MASSENEMY_API UHostileMassSettings : public UDeveloperSettings {
  GENERATED_BODY()

public:
  UPROPERTY(EditDefaultsOnly, Config, meta = (ClampMin = "1", ClampMax = "128"))
  int32 MaxSpawnPerTick = 64;

  UPROPERTY(EditDefaultsOnly, Config)
  TMap<EHostileType, TSoftObjectPtr<UMassEntityConfigAsset>> EntityConfigs;

  // ...
}
```

The settings can then be accessed in other systems.

```c++
bool UHostileMassSubsystem::ShouldCreateSubsystem(UObject* Outer) const {
  // ...

  const auto Settings = GetDefault<UHostileMassSettings>();
  if (!Settings) return false;

  // ...
}
```
